# Local scrolling-message settings

The desktop editor is now an in-panel `OriginalMarqueeDialog`, using the decoded XML's 674-pixel width, 60-pixel title/edit rows, 614×175 editor, 30-pixel side margins and the original -45 vertical offset. The unused Java dimension constants are not the rendered layout. The recovered dialog/background/button colors are drawn natively. Clear edits the draft, cancel/Escape discards it, confirmation saves, and outside taps keep the dialog open. The original local-mode radio reloads saved text. Online mode is visibly unavailable; it does not make a manufacturer request. WPF radio artwork remains an adaptation. Windows build 74 (run `37530596757`, commit `e8e32e7`) passed the native interaction checks. Its synthetic capture was inspected: title, modes, editor, counter and actions are visible. The report confirms saved text/counter, staged clear, cancel, outside-tap retention and confirmed persistence. The separate live YouTube probe encountered a bot sign-in challenge.

`SettingAction.getMarqueeState/setMarquee` exposes `mode` (`"1"` local, `"0"` cloud) and `localText`. The local branch stores the text and calls `MarqueeManager.updateActiveInfo`; it does not replace current/next song information or change playback. `MarqueeSettingDialog.MAX_INPUT_WORD` is 240 UTF-16 units, with a remaining-character counter and staged editing. Cloud mode invokes `DCDomain.requestMarqueeText` and remains outside this port's working local branch.

The paired Windows controller now offers GET/POST `/api/settings/marquee` for local mode, retaining the original fields and adding `maxLength`/`cloudAvailable` capabilities. Cloud mode is rejected rather than represented as a successful vendor fetch. Existing pairing, origin and revocation checks apply. The local browser editor has a 240-unit textarea, remaining count, clear, cancel and confirmation; saved text is displayed literally and wraps even when all 240 characters form one word. This is an adapted browser editor, not a claim of original phone-client visual parity.

`OriginalMarqueeSettings` reuses `tv-marquee.txt`, preserving existing saved messages and reading external changes. New saves are atomic, accept empty text for clearing and reject text over 240 units or invalid controls. The desktop editor now shares this setting and limit. TV updates preserve the overlay's current/next titles rather than borrowing the YouTube screen's queue state, which previously could replace a local song title when editing the message. The playback state directory now also supplies TV message storage, isolating verification sessions from the owner's app data. The shared TV/preview surface continues to carry the overlay.

Core checks cover existing files, exact Unicode persistence, the UTF-16 limit, invalid inputs and clearing. Native HTTP checks cover pairing, origin/revocation, persisted messages, unavailable cloud mode, rejected requests, song/idle text preservation, local queue source/title preservation and actual TV text elements. Phone-sized browser checks exercise staged clear/cancel, Unicode save, literal markup, the character counter and a 240-character unbroken message without horizontal overflow. Editing while paused does not resume playback.

Windows build 72, run `37528991835`, commit `021615c`, passed the core, native HTTP and phone-sized browser checks. The `mobile-remote/verification.json` report confirms all scoped marquee assertions; the `phone-marquee-settings.png` capture was inspected and the textarea, remaining counter, saved message and all three actions are visible. Physical-phone Wi-Fi behavior remains unverified. The live YouTube probe separately hit a sign-in challenge. Cloud retrieval, exact original radio artwork and manufacturer network-envelope compatibility remain pending; the desktop local dialog is now ported as described above.
